# Руководство по разработке проекта (CONTRIBUTING.md)

Привет! Это руководство описывает стандарты разработки,
процесс локального развертывания и правила взаимодействия
внутри нашей команды для этого репозитория.

---

## Быстрый старт (Локальное окружение)

Перед тем как начать писать код, убедись, что у тебя установлены все необходимые зависимости (Docker, Docker Compose, актуальная версия языка/рантайма).

1. **Клонируй репозиторий:**

git clone https://gitlab.informatics.ru/2025-2026/ydex/s103d/final-project-t1918
cd backend

2. **Запусти инфраструктуру:**

```bash
docker-compose up -d

```

---

## 🛠 Процесс работы над задачами (Workflow)

Мы работаем по методологии [GitFlow].

1. **Взятие задачи в работу:**

- Убедись, что задача назначена на тебя в
- Переведи задачу в статус **"В работе" (In Progress)**.

2. **Создание ветки:**

- Ветки создаются от `main` (или `developing`) в зависимости от того, что написано в задаче
- Именуй ветку по шаблону: `тип/метод`.
  > _Пример:_ `feature/AddPriorityChannels` или `hotfix/AdminPanelAuth`

3. **Разработка:**

- Пиши тесты на новый функционал.
- Следи, чтобы локально проходили тесты (`make test-all`).

---

## 🔍 Merge Request и Code Review

Когда задача готова, создай Pull Request (PR) в ветку `developing` / `main`.

- **Оформление PR:** В описании укажи ссылку на задачу и кратко опиши, что было сделано. Если логика сложная — добавь комментарии для ревьюеров прямо в код.
- **Проверка:** PR должен пройти все автоматические проверки (CI/CD пайплайны, тесты, линтеры).
- **Ревью:** Для слияния (Merge) требуется как минимум **X аппрува(ов)** от участников команды.
- **Исправления:** Все замечания в ревью обсуждаются в комментариях к PR. После исправления триггери повторную проверку.

## Стандарты кода и Линтинг

Мы пишем чистый код и придерживаемся единого стиля во всей экосистеме команды.

- **Линтеры:** Перед коммитом обязательно запускай линтер. Код с ошибками линтера автоматический CI-пайплайн не пропустит.
- **Архитектура:** Мы используем [Чистую архитектуру + Микросервисы ]. Логика хендлеров/транспорта, бизнес-логика (сервисный слой) и работа с БД (репозитории) должны быть строго разделены.
- **Ошибки:** Не глуши ошибки. Используй явную обработку и типизированные ошибки (Sentinel Errors) вместо generic-строк на верхних уровнях.

---

## Правила оформления коммитов

Мы используем соглашение **Conventional Commits**. Каждое сообщение коммита должно четко отражать, что изменилось.

Шаблон: `Краткое описание на английском/`

> - `add pagination cursor passing to recommendation service`
> - `remove expired post IDs from ZSET index`
